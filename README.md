# Riflo backend

Riflo turns a long video into content for multiple channels. Phase 1 includes X and LinkedIn posts, blogs and newsletters, carousels, then short videos for YouTube and Instagram. Editing is Phase 2; social connections, scheduling and publishing are Phase 3. Payments come later.

The backend currently supports Firebase sign-in verification, manually assigned paid access, Google Drive connection and file checks, durable private video import, and repeat generation of X/LinkedIn posts, blogs, newsletters, five-image carousels and original-source short video exports. There is no editing, payment integration or social publishing.

Imports, manual retries and generation now use authenticated finite SSE for progress and recovery, with canonical JSON saved-state reads. See the [communication policy](docs/communication-policy.md) and [implemented routes, recovery and verification](docs/communication-implementation.md). Progress notifications do not stream provider tokens or generated content.

Use the [API contract standards and reuse guide](docs/api-contract-standards.md) for each endpoint review. It defines shared contract rules, existing reuse points and known exceptions without changing the communication policy.

## Run locally

Use Node 22+ and Java 21 for Firebase emulators. Install FFmpeg separately from its [official downloads](https://ffmpeg.org/download.html); provide the absolute `ffprobe` path for intake and `ffmpeg` path for generation. Workers check these executables before starting. No system software or remote services are configured automatically.

```
npm ci
cp .env.example .env
firebase emulators:start --project demo-riflo
```

Run `npm run dev` to start the API and worker together, with logs labeled `api` and `worker`. Ctrl+C is forwarded to both services. If either watcher command exits, the other is stopped, with forced termination after five seconds if needed. An application crash leaves its watcher waiting for the next source change. To run them separately, use `npm run dev:api` and `npm run dev:worker` in separate terminals. Both load `.env`, so the worker can process queued jobs against the configured services. The API listens on port 4310; the frontend runs at `http://localhost:4311`. For local Drive consent, register `http://localhost:4311/v1/drive/connection/callback` in Google OAuth and set the same backend redirect URI. For compiled deployments: `npm run build`, then `npm start` and `npm run worker` as separate processes. The worker handles imports, generation and cleanup.

Development commands watch imported source files and restart the affected API or worker when they change, keeping terminal logs visible. A restart waits up to five seconds before forcing the old child to stop. Avoid saving worker changes during a generation: interrupted work may need lease recovery. Restart the dev command after changing `.env`. Use `RIFLO_WORKER_TRACE=1 npm run dev` for detailed worker tracing; it is off by default. Run `npm run dev` in the frontend separately; Vite already updates the browser when frontend code or styles change.

The worker logs actual job claims, saved results, discarded results and failed attempts by default. An overdue wait reports its phase and elapsed time once, followed by a settlement notice if it ends. Health checks track pending work rather than treating a running process as proof of progress. They respect configured provider budgets and do not cancel, retry or restart work. A warning is not a generation failure. Normal idle polling stays quiet. Logs contain identifiers, timings and safe error codes, not transcripts, generated content or credentials.

Set `FIREBASE_PROJECT_ID` and `FIREBASE_STORAGE_BUCKET`. Real projects require Application Default Credentials supplied outside this repository. Never commit credentials. Emulator host settings are rejected unless `NODE_ENV` is explicitly `development` or `test`. Serve the frontend through the same origin or a same-origin proxy; no CORS flow is enabled.

Checks: `npm run typecheck`, `npm run build`, and `npm test`. Tests involving Firebase skip unless emulators are available. Native video-render tests also require `FFMPEG_PATH` and `FFPROBE_PATH` in the test environment; the test runner does not load `.env` automatically. Run the full suite with:

```
firebase emulators:exec --project demo-riflo --only firestore,storage 'npm test'
```

Test files run sequentially because worker tests share global queues. Tests use fake provider responses and do not make paid AI calls. Opt-in real-model checks and human review criteria are documented in [generation evaluations](evals/generation/README.md); their default command is a dry run. Real Google consent/downloads, Deepgram transcription and Anthropic generation remain unverified without operator credentials. Firebase's Storage emulator does not enforce every Google Cloud Storage creation precondition; adapter tests verify the native no-overwrite condition is sent.

## Access and subscriptions

The client signs in with Firebase and sends `Authorization: Bearer <Firebase ID token>`. The server verifies the token, including revocation, and derives ownership from its UID. A client cannot supply a different account. Firestore and Storage rules deny direct client access; server operations enforce ownership independently.

New processing requires active access. Public trial activation is disabled by default; the opt-in lifecycle behavior is described below. For legacy/manual access, a privileged administrator can write `subscriptionGrants/{firebaseUid}` in the emulator UI or Firebase console. There is no public grant-writing endpoint. Example record:

```json
{
  "status": "active",
  "startsAt": "2026-10-18T00:00:00Z",
  "expiresAt": "2026-11-18T00:00:00Z",
  "features": ["x_posts", "linkedin_posts"],
  "limits": {
    "sourceSeconds": 1800,
    "x_posts": 10,
    "linkedin_posts": 5,
    "blogs": 0,
    "newsletters": 0,
    "carousels": 0,
    "short_videos": 0
  }
}
```

These are examples, not finalized prices or plan promises. Every quota must be an explicit nonnegative whole number. Malformed, future or expired grants grant no new processing access. A missing grant permits trial intake only when the trial feature gate is explicitly enabled. Legacy grant dates identify the allowance period; changing dates starts a new legacy period, while changing limits preserves its counters.

### Shared creation-credit grants

New grants can explicitly opt into shared creation credits. Existing administrator grants and already accepted jobs keep their per-format accounting; there is no automatic migration, historical debit or allowance reset. The pure `planGrant` builder in `src/access/plans.ts` produces the following shape without writing it to any account:

```json
{
  "status": "active",
  "accounting": "shared_credits",
  "allowancePeriodId": "unique-paid-period-2026-10",
  "startsAt": "2026-10-01T00:00:00Z",
  "expiresAt": "2026-11-01T00:00:00Z",
  "features": ["x_posts", "linkedin_posts", "blogs", "newsletters", "carousels", "short_videos"],
  "limits": { "sourceSeconds": 18000, "creationCredits": 120 }
}
```

`allowancePeriodId` is an opaque administrator-assigned ID of 8–128 letters, digits, underscores or hyphens. Keep it stable for corrections or upgrades within the same funded period. Use a fresh unique ID only for a genuinely new allowance period. Editing dates, features, brand or a Drive connection does not create a new shared ledger; the stored ledger ID is `shared-{allowancePeriodId}`. Reusing a previously funded period ID reuses its counters. Removing or invalidating a grant still revokes pending work. Ordinary expiry or renewal preserves already accepted work under its original funding identity.

The backend catalogue records lower/higher monthly offerings of $39/$69, 120/250 creation credits and 300/600 source minutes. `creationCreditCosts` in `src/access/policy.ts` is the backend configuration for new requests: one per X post, LinkedIn post, blog or newsletter; two per carousel; four per short video. One of each costs ten credits. Each accepted slot stores its immutable charge and funding period. Admission reserves the complete selection atomically; a validated, unique persisted output consumes its reserved credits once. Failed, duplicate, deleted, expired and abandoned outputs release pending credits; retries retain the existing reservation. Successful source imports consume source seconds separately and are never refunded by later generation failure or deletion. Provider usage and expense remain recorded separately for every attempt, including late discarded results.

Single-period shared `/v1/usage` responses include `accounting: {mode: "shared_credits", periodId}` and only the `sourceSeconds` and `creationCredits` meters in `limits`, `reserved`, `consumed` and `remaining`. Single-period shared capabilities include `accounting: {mode: "shared_credits", periodId, creditCosts}` and the same two limits. Legacy response meters remain per-format. Project generation availability includes optional `credits: {remaining, costs}` so Create can display prices and block unaffordable choices using its existing project request. The command transaction always checks current access and balance again. Accepted public batch slots optionally expose their snapshotted `credits`.

The versioned lifecycle implementation supports the seven-day, 15-credit, 45-source-minute trial, trusted paid transitions and separate trial/paid balances. `TRIAL_ENABLED` defaults to `false` and remains disabled in the example configuration. Internal verification may enable eligible first-import activation; public release still requires retention compatibility, abuse secret/TTL deployment and truthful offering/privacy checks. The minimum no-card abuse controls now add verified Google identity for new trials, durable keyed identity-use evidence across Firebase UID recreation, and backend request budgets for trial provider work. These engineering safeguards do not prove one Google account is one human. It does not integrate payments, roll over paid balances or automatically restore expired sources. Explicit restoration is implemented through `POST /v1/projects/:id/restore-source`: successful restoration consumes source-processing minutes, and live cached-transcript reuse requires verified source-content identity. Legacy live transcripts without verifiable identity are blocked; projects without a live transcript may restore. See [restoration contracts and limits](docs/implementation-assumptions-and-attention.md#explicit-source-restoration--implemented-independent-acceptance-pending-30-october-2026). The approved retention matrix is implemented behind `RETENTION_ENABLED=false` by default; enablement requires compatible readers, workers and cleanup plus the release checks in [the retention implementation record](docs/retention-implementation-plan.md). See [lifecycle HTTP and usage contracts](docs/trial-paid-lifecycle-api.md) for eligibility, activation order, separate period meters and compatibility. Current effective processing caps stay 30 minutes and 2 GiB per source; unmanaged legacy retention preserves the snapshotted administrator setting of 1/7/30 source days (default seven), and 30-day transcripts/outputs. For explicitly enabled managed writes, trial originals expire at trial start +14 days and transcripts/outputs at +30 days; paid originals expire at successful import +60 days, and transcripts/outputs retain while paid plus 60 days from actual paid end. Saved promise floors and surviving-resource promotion/reactivation are preserved without reviving expired or deleted content. Existing unknown records retain their saved behavior; trusted explicit adoption is separate from enablement. Catalogue source allowances do not raise those per-file caps.

`GET /v1/capabilities` returns available features, plan limits and operational bounds. Generation uses a live saved transcript or the required unexpired stored source video and remains available when Drive is not configured; missing generation providers or output storage keep it disabled. Importing still requires a configured source adapter and storage. The frontend uses these values, and the backend also checks every processing request. `generationBatchLimits` gives the maximum count of each format in one generation request (`x_posts: 2`; the other five formats: `1` each), separately from subscription-period quotas in `limits`. `services` contains `drive`, `intake` and `generation`, each with a `configured` boolean. `services.sources` reports each source separately (`drive` and `youtube`). YouTube reports `configured: true` only when its optional adapter settings are supplied; startup verifies the local tools without contacting YouTube. These describe server configuration, not live provider health, account permission or remaining allowance. Existing project reads and usage do not depend on a source adapter being configured. The frontend can allow Drive selection while intake or generation is not yet configured. `GET /v1/usage` returns limits, reserved, consumed and remaining amounts, including while inactive or trial-unstarted. Lifecycle responses expose separate trial/paid periods and aggregate active meters without activating a trial. Existing projects/results and connection deletion remain accessible to their signed-in owner after subscription expiry.

## Account and brand boundaries

A Riflo account is the verified Firebase UID that owns its projects, outputs, allowances and usage under `accounts/{uid}`. Every request must derive ownership from its verified token, never a client-selected owner ID. The current ownership boundary already supports this separation; no code restructuring or tenant framework is needed now.

The confirmed offering is **one brand per Riflo account on both paid plans**, with no extra higher-plan brand profiles for now. The backend can save and retrieve an optional brand profile at `accounts/{uid}/settings/brand`. The profile does not create another authentication identity, change paid allowances or grant another trial. Brand settings are optional writing defaults for future text and carousel-copy generation; the frontend provides settings and per-generation choices. Original short-video speech and visual rendering are unaffected. Multiple brands within one account remain a separate future feature.

The future Figma-style account switch means selecting between independent Riflo logins. It is not implemented. It will need frontend auth-session selection, cache isolation/reset and SSE teardown/reconnection for the selected UID; requests must carry that account's token so the existing backend ownership checks continue to apply. Each independent account keeps its own paid and trial allowances, with no automatic pooling. Linking authentication providers to one Firebase identity is distinct from switching independent accounts. The session and interface details need later discussion.

External provider connections are separate from Riflo login. Connecting a different Google Drive account does not sign into another Riflo identity. Drive currently stores one connection per Riflo account at `driveConnections/{uid}`; multiple provider connections require a separate review.

### Saved brand API

`GET /v1/brand` returns `{ "data": null }` before setup. `PUT /v1/brand` accepts a plain JSON profile and returns the saved profile inside `data`, after storage succeeds. Both require a verified Firebase token and return uncached JSON. Reading saved preferences is available after paid access ends. Saving requires active access under the same backend grant rules as generation; saving never consumes allowances or grants generation access. Storage ownership always comes from the token, and client-supplied owner IDs or unknown settings are rejected.

PUT replaces the complete profile: omitted settings are removed, `{}` clears all preferences, and arrays may be empty. Scalar strings are trimmed; blank scalar settings are omitted. Fields are optional and have the following maximum lengths (JavaScript string characters):

| Setting | Limit |
| --- | --- |
| `name` | 120 |
| `description` | 2,000 |
| `audience`, `voice` | 1,000 each |
| `language`, `spelling` | 80 each; plain-language preferences, no prescribed options |
| `writingExample` | 8,000 |
| `avoidPhrases` | 30 nonblank strings, 120 each |
| `colours` | 8 hex colours in `#RRGGBB` form |
| `fonts` | 5 nonblank names, 100 each; availability is not checked |

The brand JSON body limit is **99,299 bytes**, derived from every field maximum plus JSON keys, array punctuation and the six-byte Unicode escape representation of each string character. The generation body limit is **112,145 bytes**, adding its output-selection and brand-choice envelope plus the 12,000-byte controls allowance. These bounds accommodate a maximum-sized profile or writing override using multibyte text or Unicode escapes; unnecessary whitespace still counts toward the request budget. Other JSON routes retain their existing 4,096-byte limit. Free text (`description`, `audience`, `voice`, `writingExample`) allows tabs and line breaks; other fields are single-line. Other control characters, null values and incorrect types are rejected with `400 invalid_request`. Malformed JSON returns 400, unsupported content types 415 and oversized requests 413. Storage failures return a safe 503 response without private provider details. Colours and font names are stored but are not interpreted by current renderers; the interface hides those controls until supported. There is no logo upload.

### Brand preferences during generation

Existing `{ "outputs": { "x_posts": 1 } }` requests remain valid and use optional saved writing preferences. A request can also supply `"brand": { "mode": "none" }` to bypass defaults, or `"brand": { "mode": "saved", "overrides": { "voice": "Direct", "audience": "Teachers" } }` for one-time changes. Override fields are the writing/context fields above, excluding colours and fonts. Omitted override fields inherit saved values; blank scalar strings clear a saved preference for that request, and an empty avoided-phrases array clears those exclusions. Bypass mode rejects overrides. One-time choices do not update the saved profile.

The accepted batch privately stores the effective preferences, including any writing sample used for that request, under the existing accepted-job history and its retention behavior. Clearing or changing saved brand settings affects future requests; it does not purge preference snapshots from previously accepted jobs. Snapshot expiry follows the associated retained content; account writing settings and financial/idempotency audit facts have separate lifecycles. Later brand edits do not alter queued work. Idempotent replays compare normalized explicit choices, not the current saved profile; changing explicit choices requires a new request key. Default requests preserve their existing fingerprint format. Public generation responses expose only `brand.status`: `applied`, `none`, `unavailable`, or `not_applicable` (video-only requests).

Missing setup never blocks generation. A failed or slow brand read falls back to ordinary generation, reports `unavailable`, and still uses any valid explicit overrides. Authentication, active access, source ownership, input validation and allowances remain mandatory. Brand reads are capped at 1.5 seconds; this is a local request fallback, not a retry or paid model call.

Writing defaults apply to X, LinkedIn, blogs, newsletters and carousel copy. They are supplied as untrusted context alongside source data, not interpolated into trusted instructions. Source facts, attribution, qualifications, topic and output limits take priority. Context does not authorize promotion, automatic brand mentions, claimed personal experience or unsupported relevance. Samples guide style only. Explicit output language can change generated prose, while names, code, identifiers and exact quotations remain faithful. Video selection and original speech do not use writing preferences. Branded copy attempts append `+brand-v1` to their existing prompt version; unbranded prompt identities remain unchanged.

`GET /v1/capabilities` includes `brand.available`, selectable `brand.languages`, and validation `brand.limits`. These describe product choices and access, not a guarantee that every multilingual output has been quality-validated.

## Video sources

Drive requests keep their existing `{fileId, resourceKey?}` shape and idempotency fingerprints. An explicit `source: "drive"` is also accepted and normalized to that same shape. Source adapters share the bounded stream, actual media probe, private upload, ownership, allowance and cleanup flow. Unknown source metadata can keep size or duration unset until import completes. A download must finish successfully before any source is uploaded; cancellation also stops waiting for producer completion. YouTube can be configured independently of Drive with `YT_DLP_PATH` and `FFMPEG_PATH`. The frontend accepts YouTube links through the same single-action import and separate generation flow as Drive. Automated checks use fixtures; a bounded live YouTube sample has also been downloaded and probed locally.

## YouTube imports

The adapter pins `yt-dlp` 2026.10.26 and `yt-dlp-ejs` 0.8.0, with Node 24.12 or newer and FFmpeg 9.0.2. YouTube requires FFmpeg HTTP options `request_size`, `multiple_requests` and `short_seek_size`; offline startup verification checks these capabilities in addition to the pinned yt-dlp version, production options and Node/FFmpeg executables. Tool paths must be absolute. Keep the matching EJS package bundled with yt-dlp; remote component downloads are disabled. A missing runtime, solver or HTTP capability is a setup error. No API key or user cookies are used.

Set optional `YT_DLP_PATH` to the absolute yt-dlp executable and provide `FFMPEG_PATH`; Node uses the current backend executable. Both API and worker check these tools offline before starting when YouTube is configured. Leave `YT_DLP_PATH` unset to disable YouTube without affecting Drive. A configured but missing or untested executable stops startup with a setup error. No runtime package installation happens.

`POST /v1/sources/youtube/validate` requires sign-in and active access, or enabled trial eligibility; validation never starts a trial. Send `{"url":"https://www.youtube.com/watch?v=VIDEO_ID"}`. The response contains `{input:{source:"youtube",videoId},source:{source:"youtube",videoId,name,mimeType,bytes,durationSeconds,requiresProbe}}` inside `data`. Unknown size/duration are `null`. For direct import, send `{source:"youtube",url:"https://youtu.be/VIDEO_ID"}` to `POST /v1/projects` with an `Idempotency-Key`; no preliminary validation request is required. The existing `{source:"youtube",videoId}` input remains accepted. URL input is strictly parsed and normalized to the same video ID before idempotency lookup, so equivalent supported links and legacy ID requests replay the same accepted project without provider revalidation. Supplying both `url` and `videoId` is rejected. New imports check metadata once during admission, reserve allowance and queue the normal private import; the worker retains its later download checks. Existing trial activation timing is unchanged. Browser-supplied titles or metadata are never accepted. Drive's existing endpoints and project request shape are unchanged.

Only individual public/unlisted, unrestricted, finalized videos are accepted; live/upcoming, private, membership, age/sign-in and verification challenges are rejected. Supported HTTPS links are normalized to one YouTube video ID. Downloads use that fixed watch URL, YouTube-only extraction, no local configuration/plugins/netrc/cookies, bounded retries/time/output, a clean child environment and one process group. The shared importer still enforces actual bytes/duration and waits for a successful producer exit.

Video selection requires H.264 video up to 1080p and AAC audio, with a combined-format fallback. These codecs remain recognizable when yt-dlp streams through FFmpeg's MPEG-TS stdout output. FFmpeg fetches HTTP media in 10 MiB requests with persistent connections, matching the chunk size used by yt-dlp's native YouTube downloader. FFmpeg progress is disabled separately from yt-dlp progress so normal downloads do not exhaust the 64 KiB diagnostic limit. Videos without these compatible formats cannot be imported.

A canonical URL does **not** contain the downloader's later requests: redirects, media manifests and FFmpeg can contact other destinations. Before production activation, run both the API metadata checks and import worker in containers whose network policy denies private/loopback/link-local and cloud metadata destinations. This is an operator deployment requirement, not protection provided by this adapter. Local tests intentionally use loopback media fixtures through a separate test-only invocation; the bounded live sample does not verify production network isolation or every video's availability.

Primary tool references: [yt-dlp options and format selection](https://github.com/yt-dlp/yt-dlp), [FFmpeg progress controls](https://ffmpeg.org/ffmpeg.html), [EJS/runtime setup](https://github.com/yt-dlp/yt-dlp/wiki/EJS).

## Google Drive

Firebase login does not grant Drive access. Set all four Drive settings: `GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET`, `GOOGLE_DRIVE_REDIRECT_URI`, and `DRIVE_TOKEN_ENCRYPTION_KEY`. Generate the key with `openssl rand -base64 32` and keep it outside this repository. Changing it without migration makes saved connections unreadable.

Create a dedicated Google web OAuth client, configure its consent screen/test users, and register the exact callback URI. Enable Drive and Picker APIs. Browser Picker setup also needs a restricted developer key and project number. Riflo requests only `drive.file`, rather than permission to browse the whole Drive.

| Route | Behavior |
| --- | --- |
| `POST /v1/drive/connection/authorize` | Requires paid access; returns a Google URL and sets a browser cookie. Navigate that same browser to the URL. |
| `GET /v1/drive/connection/callback` | Google returns here. Validates the saved request and cookie; returns JSON, not a frontend completion page. |
| `GET /v1/drive/connection` | Returns configured/connected state without credentials. |
| `DELETE /v1/drive/connection` | Removes local credentials first, then reports whether Google revocation succeeded. |
| `GET /v1/drive/picker-session` | Requires paid access; returns a short-lived access token and expiry for Picker. Keep the token in memory. |
| `POST /v1/drive/files/validate` | Requires paid access; accepts `{fileId, resourceKey?}` and returns preliminary video details. |

Authorization requests are browser-bound, single-use and expire after ten minutes. Refresh tokens and temporary proof values are encrypted and bound to their owner. A failed reconnect preserves the working connection; disconnect/new requests invalidate older callbacks. Configure Firestore TTL on `driveOAuthSessions.cleanupAt` to remove expired records; expiry enforcement does not depend on TTL.

A private pasted link may still require selection through Picker. Arbitrary download URLs are rejected. File checks enforce downloadable video type, trash state, size and known duration. Missing duration is reported as null. Every preliminary result has `requiresProbe: true`; actual bytes still need inspection. Picker tokens remain valid at Google until expiry or revocation, even after local disconnect. Exclude credentials, authorization codes and callback query strings from infrastructure logs.

## Projects and generation

JSON request bodies are limited to 4096 bytes. JSON responses use `{data: ...}` or `{error: {code, message}}` and disable caching. The three command routes below return a finite SSE response (HTTP 200) when sent `Accept: text/event-stream`; without it, they preserve JSON 202 compatibility on the same routes. New-work access checks do not block matching accepted-request recovery.

| Route | Behavior |
| --- | --- |
| `POST /v1/projects` | New work requires active access or enabled trial eligibility; eligible first initiation starts the trial before upstream validation; accepts a supported source input and an `Idempotency-Key`; durably queues an import before acceptance. |
| `POST /v1/projects/{id}/retry-import` | New work requires active access; failed imports only. Requires a fresh `Idempotency-Key`; rechecks the original source and reserves current allowance atomically on the same project. Returns SSE or JSON acceptance; never starts generation. |
| `GET /v1/projects` | Latest 50 owned projects. |
| `GET /v1/projects/{id}` | Owned project status and safe source details. |
| `DELETE /v1/projects/{id}` | Stops pending work, releases undelivered reservations and requests content deletion. Cleanup may remain pending. |
| `POST /v1/projects/{id}/generate` | New work requires active access; confirms a new batch using a live video or saved transcript. One active batch per project. Requires an `Idempotency-Key`. |
| `POST /v1/projects/{id}/retry-transcription` | Explicit recovery of failed transcription from the stored source. Active access and an `Idempotency-Key` are required; accepts an empty body or `{}`. No output or source allowance is reserved. |
| `GET /v1/projects/{id}/operations/{kind}/{operationId}/events` | Read-only authenticated finite SSE for an exact owned operation; kind is `import` or `generation`. Never starts or retries work. |
| `GET /v1/projects/{id}/generation` | Current batch ID, progress and individual output statuses. |
| `GET /v1/projects/{id}/generation/availability` | Project action and transcription-recovery guidance; available before the first batch. See [Generation availability](#generation-availability) for the complete response. |
| `GET /v1/projects/{id}/outputs` | Available generated outputs. |
| `GET /v1/projects/{id}/outputs/{outputId}` | One owned output. |
| `GET /v1/projects/{id}/outputs/{outputId}/download` | Private plain-text attachment. |
| `GET /v1/projects/{id}/outputs/{outputId}/assets/{assetId}/download` | Private owner-checked PNG or MP4 attachment. |

Request keys contain 8–128 letters, numbers, underscores or hyphens. Repeating a key with the same selection returns its existing request; changing the selection returns a conflict. Intake replay does not depend on Google being available again. A superseded accepted import returns safe JSON 409 with its original accepted identity; read the current project separately. See the implementation inventory for the exact envelope and legacy recovery behavior.

Project JSON from detail/list reads and create/retry acceptance (including replay) contains exactly `id`, `importOperationId`, `status`, `source`, `sourceUrl`, `createdAt`, `sourceExpiresAt`, `errorCode` and `importRetry`. `source` contains `source: "drive" | "youtube"`, the corresponding `fileId` or `videoId`, `name`, `bytes` and `durationSeconds`; unknown size/duration remain `null`. Legacy Drive records also return `source: "drive"`. Dates are ISO strings; `importOperationId`, `sourceUrl` and `sourceExpiresAt` may be `null`. `errorCode` is the saved import error only while status is `failed`, otherwise `null`; internal error history remains retained. `importRetry` keeps its existing guidance and optional allowance fields described below. Internal `updatedAt`, `attempts`, `source.mimeType`, `source.canDownload` and `source.requiresProbe` are omitted. Deploy a frontend tolerant of these omissions first, then deploy this backend separately; existing request inputs and source-validation responses keep their current contracts.

The client persists the exact request identity before submission. After import acceptance, navigation closes that POST observation and the visible project resumes through read-only GET observation; generation normally keeps its POST stream while the view remains active. Hidden tabs, navigation, logout and terminal outcomes close observation without cancelling durable work. Saved reads coalesce notifications, recover after reconnect, and retry the final read independently of work submission.

Generation accepts `{}` for the default two X posts and one LinkedIn post, or `{ "outputs": { "x_posts": 1, "linkedin_posts": 0 } }` for a subset. Counts are capped at two X posts, one LinkedIn post, one blog, one newsletter, one carousel and one short video. Additional formats are opt-in: for example, `{ "outputs": { "blogs": 1, "newsletters": 1 } }` generates those formats without short posts. A project can have successive generation batches, with one active batch at a time. A fresh key requests another batch after the current one finishes; replaying an accepted key returns that original batch, even after newer batches or expiry. Reusing a key with different outputs returns `idempotency_conflict`. Historical outputs remain available through their usual download endpoints until their own expiry. Subsequent batches have distinct slot, asset, job and usage identities. Source-only intake remains valid until generation is requested.

Create includes recent, retained outputs from the same project and format in the existing model request. History is untrusted exclusion context, not another factual source or instructions: a new result should use a different supported angle, not merely change wording or a title. The source transcript and current writing preferences remain authoritative. Context contains at most 12 items and 8,000 serialized characters, with written excerpts capped at 900 characters per item. No extra model call summarizes or judges history; added input tokens remain part of measured provider usage and cost.

Delivery checks all retained same-format outputs in its allowance transaction. Exact duplicate posts, structured written/carousel content, or ordered final clip ranges fail with `duplicate_generated_output`, consume no output allowance, preserve provider cost, and durably queue discarded assets for cleanup. Source minutes already consumed on import are not refunded. Case, punctuation, numbers, internal whitespace and code formatting remain meaningful; legacy single-range clips normalize to the current range representation. Expired outputs do not block new delivery, and different formats may reuse the same lesson. This prevents exact repeats, not every semantic or perceptual similarity; bounded prompt history can omit older outputs. There is no automatic paid regeneration. Provider history remains bounded in prompt size. Managed projects use private canonical fingerprints for indexed exact comparisons; legacy projects retain the compatibility scan until the explicit bounded hash proof completes.

Set `ANTHROPIC_API_KEY`, `DEEPGRAM_API_KEY` and `FFMPEG_PATH` to enable generation. `ANTHROPIC_TEXT_MODEL` defaults to `claude-sonnet-5-5` for blogs, short posts and carousel copy; `ANTHROPIC_NEWSLETTER_MODEL` independently defaults to `claude-opus-5-5` for newsletters, and `ANTHROPIC_VIDEO_MODEL` independently defaults to `claude-opus-5-5` for clip selection. Deepgram defaults to `nova-3`, with configurable transcription language. Migration: `ANTHROPIC_TEXT_MODEL` previously also selected the video and newsletter models; set `ANTHROPIC_VIDEO_MODEL` and `ANTHROPIC_NEWSLETTER_MODEL` explicitly to retain those routes. Opus 5.5 uses its default always-on adaptive thinking; Sonnet 5.5 retains `between_tools`. Missing keys keep generation disabled. Claude handles generation; Deepgram handles speech. Private source bytes become bounded mono WAV audio locally, then stream directly to Deepgram without a public URL. The timestamped transcript is saved once and reused across outputs.

Rate snapshots follow the selected model for creation and any existing writing length correction. The exact default model IDs use standard synchronous API prices verified on 2026-10-31: [Sonnet 5.5](https://platform.claude.com/docs/en/models/sonnet-5-5/overview) costs $2 input / $10 output / $0.10 cache-read per million tokens; [Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/overview) costs $4 / $20 / $0.20 respectively. `ANTHROPIC_*_MICROS_PER_MILLION` overrides apply to the configured writing model; `ANTHROPIC_VIDEO_*_MICROS_PER_MILLION` and `ANTHROPIC_NEWSLETTER_*_MICROS_PER_MILLION` overrides apply to their respective models, inheriting writing overrides only when model IDs match. Unknown models retain unknown prices unless explicitly configured. Cache-write prices remain unknown because stored usage does not identify the cache TTL; supply a cache-write override only when that TTL and price are known. A returned model that differs from the rate snapshot leaves the cost unknown. Model routing does not guarantee source fidelity or clip quality.

Each output uses Anthropic through AI SDK with SDK retries disabled. Durable stage retries are tracked separately. The model receives the transcript as source data in the completed local-read tool result, with no executable tools and tool choice disabled. Structured output is checked again by the backend: short-post responses use `{status, text}` and successful posts are saved as plain text. X uses the official weighted 280-character parser, and LinkedIn is limited to 3000 characters. Prompts are versioned. These safeguards do not prove factual accuracy or output quality; real-model evaluation is still needed.

Blog results retain `{status, title, bodyMarkdown}` in their `data` field; newsletters retain `{status, subject, previewText, bodyMarkdown}`. Their `text` field is a readable export, so existing private TXT downloads work for every text format. Blogs allow at most 1200 body words/16000 body characters and a 120-character title. Newsletters aim for 1000–1200 body words when the source supports that depth, with a maximum of 1500 words/21000 body characters, a 100-character subject and 160-character preview. Their subject and preview complement each other. Each edition offers one clear reader benefit, using a developed letter, practical lesson or connected ideas as the source supports. Openings, paragraph lengths and endings vary naturally; anecdotes, fixed section counts and CTAs are not required. The draft preserves source perspective without borrowing the speaker’s identity or adding outside material. There is no minimum length: a short source should produce a short draft. A writing generation attempt may make one bounded technical length-correction call when an otherwise eligible candidate exceeds hard word or character limits. The correction uses the same selected model and source; both calls count toward internal provider cost, with no extra customer credits for the correction. This is not a semantic retry. If the corrected result still fails validation, the output fails. Historical per-call usage metadata remains readable. HTML, images and links are unsupported. A structured `insufficient_source` result fails that output, releases its allowance, and preserves any other successful output. It never becomes a fabricated or empty delivered result.

Long-form generation uses the same saved transcript, direct Anthropic adapter, stage retries and usage ledger. `GENERATION_LONG_FORM_MAX_OUTPUT_TOKENS` defaults to 4096 for long-form responses and carousel copy, separately from the short-post ceiling. Prompt and model versions are recorded internally per output; no web research, sending action or editing step is added.

Output list and single-output JSON contain `id`, `feature`, `text`, ISO `createdAt` and `expiresAt`, plus optional validated structured `data` and `assets`. Stored `model`, `promptVersion`, private storage paths and other internal fields are excluded from these public projections. Provider metadata remains in stored outputs and private usage history. TXT downloads continue to return the saved `text`.

A carousel is opt-in with `{ "outputs": { "carousels": 1 } }`. Claude supplies only five bounded title/body pairs. A fixed local Sharp template renders five 1080×1080 PNGs; the model cannot supply markup, layout, assets, fonts or URLs. Slide titles allow 80 characters/12 words and bodies allow 240 characters/45 words. These are product bounds, not a claim of compatibility with every social platform.

Carousel outputs retain the validated copy in `data` and safe image metadata in `assets`, including relative owner-checked download paths. Cloud storage paths and public URLs are never returned. The carousel consumes its accepted allowance (two credits for a shared-credit grant, one legacy carousel unit) only when all five images have been created and the output record is saved. A failed render removes its own partial images, preserves measured Claude usage, and leaves no delivered carousel. Failed/stale attempts and expired/deleted outputs queue private image deletion; the worker retries unfinished cleanup. Delivered images retain their own 30-day lifetime independently of source expiry. No ZIP/PDF export or additional image provider is included.

A short video is opt-in with `{ "outputs": { "short_videos": 1 } }`. Claude prefers one continuous excerpt and may select up to three chronological, non-overlapping excerpts when that produces a clearer standalone idea. The combined selected duration is 10–60 seconds, using exact saved word timestamps within the actual source duration. The opening must be truthful source speech, and the ending must preserve the explanation, qualifications and payoff. An unsuitable source fails that slot without inventing a clip. FFmpeg exports the original video and audio as a 720×1280, 30 fps H.264/AAC MP4, fitting the full picture with padding. There is no generated video, face cropping, caption editor or publishing step. These are product export settings, not a claim that every platform accepts every upload.

The clip has an owner-checked MP4 download path. A 0.1-second verification tolerance accounts for encoded audio/video timing. The slot consumes allowance only after the validated file and output record are saved. Failed rendering still retains measured Claude usage. Video files use the same attempt cleanup and effective output retention policy as carousel images.

## Processing, allowance and cost

Per-video source caps follow backend-authorized access: trial 30 minutes/3,000,000,000 bytes, lower paid 45 minutes/5,000,000,000 bytes, higher paid 60 minutes/6,000,000,000 bytes. Manual/legacy access and historical jobs without a saved cap retain 30 minutes/2 GiB. Paid eligibility supplies the cap even when remaining trial seconds fund the import. Creation and explicit import retry save the accepted cap; automatic attempts and exact accepted replay preserve it. These are admission bounds, not a measured large-file capacity promise; local acceptance and throughput/cost release gates are tracked in [assumptions and attention](docs/implementation-assumptions-and-attention.md#larger-source-readiness--30-october-2026). One active project and two waiting projects per account remain. Import checks actual bytes/video streams independently of provider metadata. Unknown duration reserves the full accepted duration cap; known duration reserves whole seconds rounded up and is adjusted after inspection. Monthly/trial source totals are unchanged and no source-count cap is added.

Import status `source_ready` means the video is available. New imports also prepare their transcript: after local video validation, storage upload and transcription run concurrently, and creating content requires both to be ready. The `preparation` field reports this separately from source status. Source-only legacy projects retain on-demand transcription. See [import preparation, recovery and cost implications](docs/import-transcription.md). Generation then produces individual outputs, ending completed, partial or failed. Successful outputs survive another output's failure. Worker claims are renewed; expired or replaced claims cannot save content or charge allowance. Bounded processing stages allow two additional transient attempts and a 24-hour total lifetime, except eager and explicit transcription retries never automatically repeat a paid or ambiguous dispatch. The stage timeout and output-token ceiling are configurable. The ledger records whether a provider request was invoked.

Successful import atomically consumes the measured source duration, rounded up to whole seconds, in the original accepted allowance period. Failed imports release their reservation. Transcription/output failures and later source deletion or expiry do not refund a successful import. Creating a generation batch reserves the accepted shared-credit charges or legacy output units atomically; an output consumes its reservation only after successful storage. Failed outputs release their reservations. Retries and duplicate requests do not consume allowance twice.

Compatibility: already imported records with an unsettled legacy reservation retain first-delivered-output settlement. An uncharged legacy source still needs source allowance when its transcript is cached; reuse avoids another transcription request, not the legacy source debit. Existing consumed sources are not charged again. There is no bulk migration or debit merely from reading an older project.

New processing requires active access; enabled eligible first-import initiation establishes trial access before upstream validation. Already accepted imports and generations keep their original-period reservation through ordinary expiry or renewal; delivery settles that period, without taking allowance from a new one. A missing, malformed or non-active grant blocks remaining work. Removing a format within the same period also withdraws its permission; a later renewal's different feature set does not retract accepted work. Source, transcript and processing deadlines still apply. Lost ownership, project deletion and access withdrawal cannot deliver an output or charge a replacement worker's reservation.

New imports save their original source allowance limit so measured-duration adjustments stay within that budget. Older imports without this snapshot can only expand under a matching, unexpired grant; otherwise the measured duration must fit their existing reservation. New reservations use whole seconds rounded up, while older accepted fractional generation reservations remain valid. Missing reservations never authorize spending.

Private `accounts/{uid}/usageEvents` records identify the project, stage, output, attempt, provider, model, prompt version, credential source and timing. They track transcription seconds, uncached/cached token categories and reported usage when available, including failed/discarded attempts. A late provider response may update cost history without restoring deleted content or consuming allowance.

Validation failures also record a safe `validation` detail: the failed rule, field, and applicable numeric measurements. For example, an oversized X post records `character_limit`, `text`, its weighted length and the limit. Logs include the rule and field; neither logs nor usage events retain the rejected content. Public error codes and retry rules stay unchanged.

Optional price settings in `.env.example` use USD millionths. Cost is estimated from measured quantities and the saved rate snapshot; missing prices or quantities remain unknown, not zero. Infrastructure cost remains unknown until measured prices exist. User allowance and company expense stay separate. There is no cost dashboard, payment provider, user-key management or automatic dollar-budget pricing system yet. Maximum input size, output tokens, timeouts, output count and attempts bound provider work.

## Retention and layout

With `RETENTION_ENABLED=false`, unmanaged legacy sources preserve their snapshotted 1-, 7- or 30-day retention (seven days when omitted) from successful import, and legacy transcripts/outputs preserve their saved 30-day promises. Managed writes use the trial/paid clocks described above. Source expiry marks `source_expired` and preserves transcripts and outputs through their own effective deadlines. User deletion removes all content and cancels pending generation; delivered allowance and private cost history are retained. Owned payload deletion keeps permanent opaque zero-byte object barriers at immutable attempt paths; these prevent delayed create-only uploads from recreating deleted payloads. These objects contain no content, but remain stored objects and incur applicable metadata/operation costs. Normal success/failure removes local temporary files; the worker also removes abandoned Riflo temporary directories older than 24 hours. Keep the worker running for cleanup. `firestore.indexes.json` declares the collection-group indexes required by source, transcript and output expiry queries. Deploy these indexes and private rules to the chosen Firebase project before enabling production processing; emulators do not verify production index availability.

### Retention policy and repeat generation

For the unmanaged legacy branch, source retention can be set by a validated `subscriptionGrants/{uid}.sourceRetentionDays` value of 1, 7 or 30; omitted values use seven days. This is an administrator setting, not a public billing tier.

- `src/access/policy.ts` owns the backend defaults and capabilities. Admission snapshots the current grant’s duration on the project, including an explicit failed-import retry. Successful import completion saves an absolute `sourceExpiresAt` and immutable import anchor. Unmanaged records keep the saved deadline; managed reads/replays reconcile effective retention with authoritative promotion/tenure facts. Firestore is the expiry authority. Source object metadata does not publish a separate, potentially inconsistent expiry.
- Source cleanup preserves live transcripts and delivered outputs. It cancels pending source-dependent transcription and video clips, while text and template-based carousel work can finish from a live transcript. Timestamp checks prevent new paid provider invocation and result admission after expiry, before cleanup runs. The worker attempts to abort at the earliest required source, transcript or batch deadline. A paid request already accepted by an external provider cannot be undone; its eventual usage and cost are still recorded. Explicit project deletion still removes the transcript and cancels all work.
- Transcripts save `createdAt` and `expiresAt` on successful transcription. Legacy records use their saved creation time or the original batch creation time, never read time. Reads, claims, provider admission, renewal and result saves reject expired transcripts; bounded cleanup removes them and backfills fixed legacy dates.
- Repeat generation uses a live saved transcript without downloading or transcribing again and reserves only the requested output allowance from the current subscription period. Source seconds already settled are not charged again. Text posts, blogs, newsletters and template carousels remain available after video expiry while the transcript lives; short clips require the original video. Without the required resource, `requires_reimport` tells the frontend to request an explicit import. New batches never extend transcript or existing output expiry. Delivered outputs retain their separate effective retention deadline.
- Expired sources never trigger a hidden upstream download or transcription. Reimport must be an explicit user action with fresh source and allowance checks and duplicate-job protection. Retention does not include unlimited imports or generation.

Application cleanup is not a promise of immediate permanent deletion or immediate cost savings. Before offering retention tiers, verify the bucket's soft-delete, versioning, lifecycle and retention-lock settings, Firestore backups/PITR, deployed indexes/rules and cleanup health. Stored copies may remain billable after an application deletion; the emulator cannot establish cloud erasure or billing behavior.

## Code layout

`src/sources/` contains the shared video-source contract and source adapters. `src/sources/drive/` groups the Drive adapter, Google connection, protected tokens, Picker access and file metadata; the YouTube adapter is beside it in `src/sources/youtube.ts`. `src/projects/` owns the shared import pipeline, project records, storage and video inspection. `src/generation/` owns generation, providers, prompts and rendered outputs. `src/access/policy.ts` sets backend access and limits; `src/http/` handles HTTP requests. `src/firebase.ts` connects these pieces to Firebase.

Saved generation progress, outputs and private downloads remain readable when AI keys are removed, provided Firebase and storage are configured. Processing capabilities stay disabled and new generation requests return `generation_not_configured`.

Failed imports expose `importRetry: {available, reason, availableAt}` in project reads. `source_access_required` means the original video must become accessible; `revalidation_required` means its current metadata/access must be checked again. These are an invitation to recheck, not a guarantee the provider will allow it. Retrying only applies to failed imports, not expired/deleted sources or failed generation. Failed-project detail reads check the current subscription period and source allowance before enabling Retry. `importRetry.allowance` reports `{requiredSeconds, remainingSeconds}`; insufficient allowance disables retry with `allowance_exceeded`, and inactive access with `subscription_required`. Required seconds use the last known duration (or the maximum for unknown duration); fresh source validation can change the final requirement. List responses retain lightweight retry hints. A rejected `POST /v1/projects/{id}/retry-import` returns HTTP 403 with `error.code: "allowance_exceeded"` for the fixed plan allowance, optionally including `error.allowance: {requiredSeconds, remainingSeconds}` (nonnegative numeric seconds from the atomic reservation check; remaining allowance may be fractional). A temporary retry cooldown returns HTTP 429 with `error.code: "retry_cooldown"` and `Retry-After` seconds. The backend rechecks subscription, queue and allowance in the reservation transaction. Reuse the same request key after an uncertain reply; a new key represents a new manual attempt. Each accepted manual retry allows the existing three automatic attempts with a fresh deadline; overall attempt numbers and usage history never reset. Cleanup compares the expired snapshot before invalidation and again before completion, and deletes only the old attempt paths.

A terminal failed import has a 60-second per-project cooldown (`operationalLimits.importRetryCooldownSeconds`). During it, `importRetry.available` is false with reason `retry_cooldown` and an ISO `availableAt`; early POSTs return 429 and `Retry-After` without contacting the source. This is not an account-wide abuse limiter; separate account request-rate hardening remains future work.

### Generation availability

`GET /v1/projects/{id}/generation/availability` returns uncached `{data: ...}` for the signed-in owner, including before any batch exists. Reading it does not reserve allowance or invoke providers.
