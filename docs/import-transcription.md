# Transcript preparation during import

New imports prepare their transcript after the complete video has downloaded and passed byte, identity, duration and media validation. Storage upload and transcription then run concurrently against the validated local file. The worker retains that file and its scratch reservation until both operations settle. It still handles one project's intake at a time.

`Project.preparation` distinguishes `pending`, `transcribing`, `ready` and `failed`. `ready` means transcript work is durably committed, even if its staged transcript is still hidden while video upload finishes. It does not authorize content creation. Optional `transcriptionStage` reports observed `preparing_audio` or `transcribing` work, recorded in the existing fenced claim and provider-dispatch commits without extra background writes. `source_ready` continues to mean that the video is stored; creating content also requires the transcript. Import progress can report `transcribe` with zero transferred bytes and an unknown total after upload finishes. This stage has no invented percentage or time estimate. A zero-output generation batch uses the `import_transcription` intent. Existing projects without preparation metadata keep the on-demand transcription fallback.

The importer checkpoints the uploaded source independently of transcription. A retry can reuse that exact receipt instead of downloading and uploading again. Transcription uses the existing provider dispatch journal, usage events, validation, retention and retry machinery. While upload is incomplete, the shared transcript carries an import operation, source hash and measured duration and is inaccessible to generation. Source completion atomically promotes the matching retained transcript and settles the actual source minutes once. It preserves the saved source if transcription fails, so the existing explicit Retry transcript action can recover without reimporting.

The intake lease is authoritative while both branches run. Local transcription does not renew a second lease. Provider dispatch and result writes recheck intake ownership. A paid or ambiguous transcription attempt is not automatically replayed; explicit retry follows the existing transcript retry policy. Positively undispatched preparation failures may use bounded retries. A successfully committed staged transcript is reused when an upload retry validates the same source. Terminal source failure removes staged content and queues saved upload cleanup while retaining provider usage evidence. This does not promise exactly-once external billing when a provider response is lost.

Transcription has no new creation-credit charge. Successful source import consumes source minutes using the existing settlement rules, including when transcription fails. Provider transcription cost now occurs during every new import, including videos for which the user never creates content. Measured provider duration and configured rate snapshots remain in usage events; unknown measurements remain unknown. This changes when and how often provider costs occur, rather than establishing a cost reduction.

Verification uses generated media, mocked providers and isolated `demo-riflo` emulators. No live provider call, account migration, queue reset, application restart or production deployment is part of this change. The unrelated stalled live job and Firestore responsiveness problem are not fixed by this feature.

## Parallel import status acceptance (2026-11-01)

The status display uses measured download bytes, then upload bytes while video storage and transcription run concurrently. A durably committed transcript sets `preparation: ready` even while its source is still importing, allowing “Saving video” with the upload bar. Creation and transcript reads still require the retained source and existing staged-transcript gates. When upload finishes first, “Preparing transcript” uses the observed `preparing_audio` or `transcribing` substage. These two markers share the existing fenced claim and provider-dispatch commits; there are no new background transactions or polling. Queued work, failures, and explicit retries retain their actual states, without estimated percentages or completion times.
