# Communication migration implementation inventory

Implemented and locally verified: the backend and client use finite SSE with canonical JSON saved-state reads. JSON command responses remain available for compatibility. The authoritative behavior is [communication-policy.md](communication-policy.md); deployment-path transport behavior remains unverified.

## Routes and saved records

The existing authenticated command routes accept `Accept: text/event-stream`: `POST /v1/projects`, `POST /v1/projects/:projectId/retry-import`, and `POST /v1/projects/:projectId/generate`. Their existing JSON body and `Idempotency-Key` contracts apply. No preliminary JSON request is necessary. Without that Accept value they retain their JSON 202 response for compatible clients; this is response-format compatibility on the same command resource.

Read-only observation uses `GET /v1/projects/:projectId/operations/:kind/:operationId/events`, with kind `import` or `generation`. It authenticates and checks the account's project and exact operation before streaming. It never admits work. Existing JSON project, generation, and output reads remain canonical, including after subscription or provider configuration changes.

Imports now store an opaque `importOperationId` on the project and its accepted intake/retry key in the same transaction as `intakeJobs`. Automatic attempts retain that ID; each deliberate manual retry gets a fresh ID. Replay returns the original accepted identity; when a newer round replaced saved state, the command returns the superseded resolution described below. Generation uses its existing batch IDs, generation request mappings, and archived batches. Accepted matching keys resolve before new-work configuration/access/source gates; mismatched inputs conflict. Independent workers continue to own execution and commit outputs and terminal state transactionally.

Request mappings have no TTL or deletion cleanup in this implementation and remain supported for the life of their stored account records. If a mapped record is missing, recovery explicitly fails `request_unresolved`; it never silently admits replacement work. Legacy import keys without operation IDs still return their saved project through JSON replay and never start duplicate work. Their streaming submission returns JSON 409 `legacy_observation_unavailable`; clients should read saved project state rather than invent an identity. Replaying an accepted import key after its operation was replaced returns HTTP 409 JSON `error: { code: operation_superseded, message, accepted: true, operation: { projectId, kind: import, id } }`, where operation identifies the original accepted request. It never labels the original operation with a newer operation’s outcome. The client resolves only the matching pending request and reads the current project separately; it must not automatically generate another request key. Direct observation of a known old operation whose current project/batch was replaced emits a terminal `superseded` observation outcome; this is not a persisted failure of either operation.

## Stream contract

Events are `accepted`, `changed`, `terminal`, and `stream_error`. Each JSON data envelope contains `version: 1` and `operation: { projectId, kind, id }`. Accepted and initial changed notifications contain `refresh: true`; they instruct the client to read canonical state. Domain notices contain `status`, `terminal`, optional terminal `outcome` (`succeeded`, `partial`, `failed`, `superseded`), and generation `ready`/`failed` counts. Observation errors expose only a safe `code`. No provider chunks, output content, storage paths, leases, or internal error messages are sent.

The backend establishes a listener before its immediate refresh notification. The listener's first committed snapshot also catches completion before attachment. It deduplicates the minimal status/count projection and listens only to the project for import or current batch for generation, never all outputs or worker lease records. A terminal notice is based on committed saved state. Clients must coalesce refreshes, follow up when notifications arrive during reads, and perform/retry a final saved read after a terminal notice. Transport closure alone proves no business outcome.

Preheader failures use ordinary safe JSON HTTP errors. Once headers are sent, listener failures emit `stream_error` then close without modifying work. Server shutdown uses `server_shutdown`, lifetime/credential deadline uses `stream_expired`, and revoked/invalid ongoing authentication uses `authentication_required`. Transient verification-service failures use `observation_unavailable`, preserving the session and allowing bounded observation recovery. The client must renew authentication before reconnecting and distinguish authentication recovery from transient observation failure.

## Connection bounds and hosting

`STREAM_MAX_MILLISECONDS` configures the API maximum lifetime (default 300000, positive timer-safe integer). Credential `exp` can shorten it. Heartbeats run every 15000 ms and recheck the original token with Firebase's revocation-aware verification, with at most one check in flight per stream. A revoked or disabled credential is therefore detected at the next completed heartbeat check, and each connection is additionally capped by expiry and maximum lifetime. Heartbeats are comments and never business progress.

Notification backpressure closes a connection on the first false `response.write`, bounding buffering to Node's write high-water mark plus one small notification. There is no application queue or durable event log. All disconnect, terminal, failure, deadline, backpressure and shutdown paths release listeners and timers. Shutdown aborts observation before closing the HTTP server; work remains durable and independent.

Responses send `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`. Real hosting/proxy delivery and idle timeout behavior still require deployment-path verification; local isolated HTTP checks cannot establish that guarantee. No production service, provider, emulator, or cloud worker is needed for the added isolated tests.

## Client lifecycle and verification

The client persists the original request identity and input for its signed-in account before submission. After import acceptance it navigates to the project, closing the POST observation; the visible project resumes through the exact-operation GET stream. Generation normally retains its POST stream while the view remains active. Visibility changes, navigation and logout release observation and timers without cancelling durable work. Notifications trigger coalesced canonical reads with a follow-up read when a change arrives during an in-flight read. Terminal notification requires a final saved read, whose retries do not resubmit work. Session or operation changes prevent late reads from replacing the active view. Transient observation recovery uses bounded backoff and polling fallback without parallel polling beside a healthy stream.
